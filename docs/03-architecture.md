# Архитектура

## Ключевое решение: шаблон под форк

Выбранная модель — **один инстанс = один продукт**. Под новый продукт репозиторий клонируется,
в нём меняются конфиг и оформление, логика приезжает из апстрима.

Что это даёт: простую схему (никакого `tenant_id`, никакой изоляции в каждом запросе),
полную свободу в редизайне, независимые деплои и базы.

Чем за это платим: N инстансов надо обновлять. Поэтому **главная инженерная задача шаблона —
сделать так, чтобы форк никогда не правил общий код**. Если форк начал лезть в домен и запросы,
через три месяца апстрим-обновления перестанут мержиться, и вместо шаблона получится
три несвязанных проекта. Ниже — как этого не допустить (см. [Правила форка](#правила-форка)).

## Стек (рекомендация)

| Слой | Выбор | Почему именно так |
|---|---|---|
| Фронт + бэк | **Next.js (App Router) + TypeScript** | Нужен SSR для SEO (FR-181..184) — портал фидбэка индексируется и приносит трафик. Один язык на весь стек, серверные экшены закрывают мутации без отдельного API-слоя. |
| БД | **PostgreSQL** | Требуются частичные индексы, `tsvector`, `pg_trgm`, генерируемые колонки, триггеры для счётчиков — всё из [02-data-model.md](02-data-model.md) написано под Postgres. |
| ORM/миграции | **Prisma** | Версионированные миграции — обязательное условие обновляемости форков (NFR-04). Сырой SQL для триггеров/индексов кладём в отдельные миграции. |
| Аутентификация | **Auth.js (NextAuth)** | Magic link из коробки + OAuth-провайдеры включаются конфигом (FR-172). SSO-провайдер по подписанному JWT дописывается как кастомный provider (FR-173). |
| Стили | **Tailwind + CSS-переменные как токены** | Редизайн форка = замена файла токенов и, при желании, вёрстки компонентов. Утилитарные классы не тянут за собой глобальный CSS, который в форках всегда разъезжается. |
| UI-примитивы | **Radix UI** (headless) | Логика поведения (меню, диалог, поповер) отдельно от оформления — ровно то, что нужно, когда оформление меняют в каждом форке. Доступность (FR-187) в базе. |
| Фоновые задачи | **pg-boss** (очередь на Postgres) | Нужны: пересчёт `trend_score`, отправка писем с ретраями (FR-309), отложенная публикация changelog (FR-166), сверка счётчиков. pg-boss не требует Redis и лишнего сервиса — для single-tenant инсталляции это решающий аргумент. |
| Почта | **Resend** (по умолчанию) через тонкий адаптер | Адаптер обязателен: часть форков поедет на SMTP/SES. Шаблоны писем — React Email, чтобы верстались как остальной UI. |
| Файлы | **S3-совместимое хранилище** (R2/S3) через адаптер | Картинки в постах и комментариях (NFR-07). |
| Деплой | **Docker + Railway/Fly.io** (альтернатива: Vercel + Neon) | Нужен долгоживущий worker-процесс для очереди — на чистом serverless он не живёт. Docker-образ ещё и позволяет форку встать on-premise, если у продукта такие требования. |
| Тесты | Vitest (домен) + Playwright (критические сценарии) | Обязательное покрытие: голосование, merge, модерация, рассылка. Именно здесь ошибки дорогие и незаметные. |

Если для конкретного продукта не нужен self-host — Vercel + Neon + Inngest вместо
Docker + pg-boss меняет только слой инфраструктуры, домен не трогает.

## Структура репозитория

```
backlog-helper/
├── config/
│   ├── product.ts          # ← ФОРК ПРАВИТ: название, домен, фичефлаги
│   ├── post-types.ts       # ← ФОРК ПРАВИТ: типы обращений, схемы форм, их workflow
│   ├── statuses.ts         # ← ФОРК ПРАВИТ: публичные и внутренние статусы + маппинг
│   ├── scoring.ts          # ← ФОРК ПРАВИТ: формула приоритета, веса сегментов, SLA
│   └── seed.ts             # ← ФОРК ПРАВИТ: начальные доски/категории/статусы
├── theme/
│   ├── tokens.css          # ← ФОРК ПРАВИТ: цвета, радиусы, тени, шрифты (CSS-переменные)
│   └── assets/             # ← ФОРК ПРАВИТ: логотип, favicon, OG-картинка
├── content/
│   ├── ru.json, en.json    # ← ФОРК ПРАВИТ: все пользовательские тексты
│   └── emails/             # ← ФОРК ПРАВИТ: тексты писем
├── src/
│   ├── core/               # ⛔ НЕ ПРАВИТЬ В ФОРКЕ
│   │   ├── domain/
│   │   │   ├── intake/     #    приём: типы, схемы форм, дедуп, fingerprint, каналы
│   │   │   ├── triage/     #    решения, needs_info, SLA, merge, модерация
│   │   │   ├── backlog/    #    элементы, скоринг, ранжирование, маппинг статусов
│   │   │   └── shared/     #    vote, trending, notify
│   │   ├── db/             #    Prisma-схема, миграции, триггеры
│   │   ├── queries/        #    чтение: возвращает готовые view-model, без ORM-объектов наружу
│   │   ├── jobs/           #    воркеры очереди
│   │   └── integrations/   #    адаптеры почты, хранилища, трекеров, вебхуков
│   ├── app/                # ⚠️ роуты Next.js: править только при добавлении страниц
│   ├── features/           # ⚠️ связка данных и UI (хуки useVote, useFeed) — правится редко
│   └── ui/                 # ✅ ФОРК ПРАВИТ СВОБОДНО: вся вёрстка и компоненты
├── packages/
│   └── widget-sdk/         # ⛔ SDK для встройки в продукт: сбор фидбэка + авто-диагностика
├── docs/
└── tools/
    └── check-fork-drift.ts # CI-проверка: не изменены ли ⛔-каталоги относительно апстрима
```

`packages/widget-sdk` публикуется отдельным npm-пакетом и версионируется независимо:
его подключают продукты, а не форки портала. Он должен работать с любым инстансом
(конфигурируется URL портала + публичный ключ) и не тянуть за собой ничего из `src/`.

## Правила форка

Эти правила — не стилистика, а условие работоспособности самой идеи «шаблон + клоны».

1. **Редизайн живёт в трёх местах:** `theme/`, `ui/`, `content/`. Всё, что нужно для нового
   внешнего вида, должно быть достижимо оттуда. Если для редизайна пришлось залезть
   в `core/` — это баг шаблона, и фиксить его надо в апстриме, а не в форке.
2. **Ни одного хардкоженного цвета/шрифта/отступа в компонентах.** Только токены
   (`var(--color-accent)`, классы Tailwind, замапленные на токены). Поэтому в
   [02-data-model.md](02-data-model.md) у статуса хранится `color` как имя токена, а не hex:
   иначе после редизайна бейджи статусов останутся из старой палитры.
3. **UI-компоненты не обращаются к БД.** Данные приходят пропсами из `queries/`.
   Тогда переписывание вёрстки физически не может сломать выборку и её индексы.
4. **Все различия между продуктами — данные, а не код.** Статусы, доски, категории,
   **типы обращений и схемы их форм**, внутренние статусы и их маппинг на публичные,
   формула приоритета, веса сегментов, политики SLA, типы changelog, лимиты, half-life
   для trending, набор OAuth-провайдеров — всё в `config/`.
   Ветвлений вида `if (product === 'foo')` или `if (type === 'bug')` в шаблоне быть не должно:
   различия в поведении типов описываются полями `post_type`, а не условиями в коде.
5. **Фичефлаги вместо удаления.** Продукту не нужен changelog — `features.changelog = false`,
   а не «вырезали страницу в форке». Вырезанное апстрим потом не сможет обновить.
6. **Синхронизация с апстримом:** в форке `git remote add upstream <template>`,
   обновление — `git merge upstream/main`. CI форка запускает `tools/check-fork-drift.ts`:
   если в `src/core/**` есть локальные отличия от апстрима — предупреждение в PR.
   Это не запрет, а сигнал «ты создаёшь долг».
7. **Шаблон версионируется** (semver + CHANGELOG). Миграции БД — только вперёд-совместимые:
   форк должен уметь применить новые миграции, не потеряв свои данные.

## Порядок запуска нового продукта

```bash
git clone <template> feedback-myproduct && cd feedback-myproduct
git remote rename origin upstream && git remote add origin <new-repo>
cp .env.example .env            # DATABASE_URL, AUTH_SECRET, RESEND_KEY, S3_*
# правим config/product.ts (название, домен, доски, статусы) и theme/tokens.css
pnpm install && pnpm db:migrate && pnpm db:seed && pnpm dev
```

Цель — чтобы этот список никогда не разрастался: новый продукт стартует правкой
конфига и токенов, без чтения кода.

## Открытые вопросы к следующему этапу

- **SSO**: как именно продукты будут отдавать пользователя порталу — подписанный JWT
  (как у Canny) или полноценный OIDC? Первое проще для собственных продуктов, второе
  универсальнее. Решать до реализации FR-173, потому что от этого зависит модель `app_user`.
- **Анонимный фидбэк**: в v1 сознательно нет (см. раздел 6 спека). Если для какого-то
  продукта он обязателен — это меняет инвариант «один пользователь — один голос»
  и должно проектироваться отдельно, а не прикручиваться флагом.
- **Локали**: нужен ли форкам мультиязычный портал (переключатель) или каждому достаточно
  одного языка. От ответа зависит, храним ли переводы контента в БД (тяжело) или только UI-словари.
- **Публичность багов**: дефолт по спеку — заголовок и статус публичны, описание/вложения/
  диагностика приватны ([FR-561](05-bug-intake.md#5-приватность-и-хранение)). Если для
  какого-то продукта баги должны быть полностью закрыты, это меняет ленту, SEO и роадмап,
  а не только флаг видимости.
- **Целевой трекер**: Linear / Jira / ClickUp / GitHub Issues. Интеграция пишется через
  общий адаптер, но первый реализованный определит форму адаптера — выбрать до этапа 3.
- **Виджет**: нужен ли он вообще для твоих продуктов. Если да — от этого зависит качество
  багрепортов и работоспособность fingerprint-дедупликации, и его стоит поднять из этапа 5
  ближе к этапу 2.
