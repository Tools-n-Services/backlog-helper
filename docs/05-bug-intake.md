# Приём обращений: идеи, ошибки, вопросы

Требования нумеруются `FR-5xx`.

## 0. Почему этого нет в референсе

В [feedback.clickup.com](https://feedback.clickup.com) баги **не собираются**: на доске
Feature Requests стоит ссылка «Report a bug», которая уводит на форму саппорта.
Это осознанное решение — публичный список ошибок выглядит как список проблем продукта,
а качество пользовательских багрепортов без диагностики близко к нулю.

Мы делаем иначе: баги — полноценный тип обращения внутри портала. Значит надо самим закрыть
три вещи, которые ClickUp обошёл: **качество багрепорта** (авто-диагностика вместо
«не работает»), **приватность** (в багах PII и скриншоты с данными клиентов) и
**отдельный жизненный цикл** (у бага «не воспроизводится» и «нужна информация» —
нормальные состояния, у идеи таких нет).

## 1. Типы обращений

Тип — не тег, а сущность, определяющая форму, набор статусов, видимость и правила ленты.

| Тип | Что это | Голосование | Видимость по умолчанию |
|---|---|---|---|
| `idea` | Запрос функции, предложение | «Мне тоже нужно» — голос = спрос | публично |
| `bug` | Ошибка, регрессия | «У меня тоже» — голос = охват проблемы | заголовок публично, диагностика приватно |
| `problem` | Боль без предложенного решения | голос = подтверждение боли | публично |
| `question` | Вопрос по продукту | нет | приватно, маршрутизируется в саппорт |
| `security` | Уязвимость | нет | всегда приватно, только owner-ы |

| ID | Требование | P |
|---|---|---|
| FR-501 | Тип обращения выбирается на входе, до формы. Набор типов и их включённость — конфиг продукта. | P0 |
| FR-502 | У каждого типа своя схема формы (набор полей, обязательность, подсказки) — данные, а не код. | P0 |
| FR-503 | У каждого типа свой набор допустимых статусов (workflow). Статусы идей и багов не пересекаются, кроме терминальных. | P1 |
| FR-504 | Тип определяет правила ленты: для `idea` сортировка по умолчанию Trending, для `bug` — по свежести и охвату (trending для багов бессмысленен). | P1 |
| FR-505 | Смена типа админом при триаже (пришло как баг, оказалось запросом функции) с сохранением голосов и комментариев. Частый кейс — должно быть одним действием. | P1 |
| FR-506 | Метка типа видна на карточке в ленте и в фильтре. | P0 |
| FR-507 | `question` не попадает в бэклог и в публичную ленту: создаётся, отвечается, закрывается. Смешивать вопросы с фидбэком — верный способ утопить и то и другое. | P2 |
| FR-508 | `security` — отдельный изолированный поток: не индексируется, не попадает ни в одну публичную выборку, уведомление только владельцам, отдельный аудит-лог доступа. | P1 |

> Возможны два размещения: типы внутри одной доски (фильтр) или отдельные доски под баги.
> Решение — конфиг продукта, но по умолчанию **отдельная доска для багов**: у них другая
> сортировка, другая аудитория и другой темп.

## 2. Качество багрепорта

Главная проблема любого сбора багов: «не работает кнопка» без версии, окружения и шагов.
Ответ на это — не длинная форма (её бросят), а **авто-сбор контекста**.

### 2.1 Поля формы бага

| Поле | Обяз. | Заметки |
|---|---|---|
| Заголовок | да | |
| Что произошло / что ожидалось | да | два поля вместо одного «описание» — иначе ожидаемое поведение никто не пишет |
| Шаги воспроизведения | да | |
| Частота | да | `всегда` / `иногда` / `один раз` — влияет на приоритет и на «не воспроизводится» |
| Severity (со стороны репортера) | да | `блокирует работу` / `мешает, есть обходной путь` / `косметика`. **Это не приоритет** — приоритет ставит команда |
| Когда началось | нет | отсекает регрессии от «всегда так было» |
| Вложения | нет | скриншот, видео, лог, HAR |
| Окружение | авто | версия приложения, браузер+версия, ОС, разрешение, локаль, часовой пояс |

| ID | Требование | P |
|---|---|---|
| FR-511 | Поля окружения заполняются автоматически и показываются репортеру в свёрнутом виде с возможностью поправить. Ручной ввод версии браузера не работает никогда. | P1 |
| FR-512 | Вложения: изображения, видео (`mp4`/`webm`, до 50 МБ), текстовые логи, HAR. Whitelist MIME, антивирусная проверка либо запрет исполняемых, отдельный бакет. | P1 |
| FR-513 | **Виджет-сборщик внутри продукта**: SDK собирает версию сборки, последние N ошибок консоли, последние сетевые ответы 4xx/5xx (с маскированием тел), breadcrumbs действий пользователя, id сессии/трейса. Репортер пишет только текст. Это единственный способ получать воспроизводимые баги. | P1 |
| FR-514 | Диагностический payload хранится структурированно (`jsonb`), показывается только команде, в публичном виде поста отсутствует. | P1 |
| FR-515 | Маскирование секретов в собранных данных на стороне SDK: заголовки авторизации, токены, `password`, номера карт — до отправки, не после. | P1 |
| FR-516 | Ссылка на session replay, если у продукта он есть (внешний id, не хранение записи у нас). | P3 |
| FR-517 | Форма бага доступна и без виджета (веб-форма на портале) — тогда окружение спрашивается селектами, а не текстом. | P0 |

### 2.2 Дедупликация багов

Для багов дедупликация работает иначе, чем для идей: похожесть заголовков помогает слабо,
зато отлично работает подпись ошибки.

| ID | Требование | P |
|---|---|---|
| FR-521 | `fingerprint` бага — хеш нормализованной подписи (тип ошибки + верхние кадры стектрейса с вырезанными адресами/id, либо `route + код ошибки`). Считается при приёме, если пришли диагностические данные. | P2 |
| FR-522 | Совпадение fingerprint → обращение автоматически привязывается к существующему багу как ещё один «затронутый», а не создаёт новый пост. Репортеру показывается статус существующего. | P2 |
| FR-523 | Поиск похожих при вводе (FR-122) для багов ищет по заголовку **и** по тексту ошибки из вложенного лога. | P2 |
| FR-524 | `affected_count` — число уникальных затронутых: голоса + привязанные обращения + инсайты. Для багов это основной сигнал приоритета вместо «голосов». | P1 |
| FR-525 | Регрессия: если баг с этим fingerprint уже закрывался как исправленный, новое обращение помечается `regression` и поднимается в очереди триажа. | P2 |

## 3. Триаж

Очередь, в которой обращение превращается в решение. Это ядро продукта — не лента и не роадмап.

### 3.1 Жизненный цикл бага

```
new → triage → confirmed → in_backlog → building → fixed → verified
         ├→ needs_info ──(нет ответа 14 дней)→ auto_closed
         ├→ not_reproducible
         ├→ by_design
         ├→ duplicate (merge)
         └→ wont_fix (с причиной)
```

| ID | Требование | P |
|---|---|---|
| FR-531 | Очередь триажа: несортированные обращения с авто-оценкой приоритета. Формула по умолчанию: `severity × частота × log(affected_count) × вес_сегмента_репортера`. Настраивается. | P1 |
| FR-532 | Действия одним кликом: подтвердить, запросить информацию, не воспроизводится, by design, дубликат (merge), won't fix с причиной, отправить в бэклог. | P1 |
| FR-533 | `needs_info` → письмо репортеру с конкретным вопросом; напоминание через 3 дня; авто-закрытие через 14 дней без ответа с возможностью реанимации ответом. Без авто-закрытия очередь заполняется мёртвыми обращениями. | P1 |
| FR-534 | Ответ репортера в `needs_info` возвращает обращение в очередь наверх. | P1 |
| FR-535 | Каждое терминальное решение требует причину, которая **уходит репортеру письмом**. «Won't fix» без объяснения — главный источник обиды на портал. | P1 |
| FR-536 | Приоритет команды (`P0..P3`) — отдельное поле от severity репортера. Сортировка и фильтр по нему. | P1 |
| FR-537 | Назначение ответственного за обращение (owner) и фильтр «мои». | P2 |
| FR-538 | **SLA первого ответа**: настраивается по типу и severity (например `bug/блокирует` — 4 часа). На карточке таймер, в списке фильтр «просрочено», отчёт по просрочкам. | P2 |
| FR-539 | Массовый триаж: выделить N обращений → одно действие (частый кейс после наплыва однотипных багов). | P2 |
| FR-540 | Шаблоны ответов (canned responses) для типовых решений: «нужны шаги», «by design, вот документация», «исправлено в версии X». | P2 |
| FR-541 | Публичный статус ≠ внутреннее состояние — маппинг описан в [06-backlog.md](06-backlog.md#маппинг-статусов). | P1 |

### 3.2 Метрики очереди

Обязательные к показу в админке, иначе процесс незаметно деградирует:
время до первого ответа (медиана и p90), возраст самого старого нетриаженного обращения,
доля закрытых как `not_reproducible` (растёт → плохая диагностика на входе),
доля `duplicate` (растёт → плохой поиск похожих), число обращений в `needs_info` дольше недели.

## 4. Каналы приёма (intake)

Портал видит только тех, кто до него дошёл, — а это самые активные пользователи,
не самые важные. Поэтому каналов должно быть несколько, и все они пишут в одну модель.

| ID | Канал | P |
|---|---|---|
| FR-551 | Веб-форма на портале. | P0 |
| FR-552 | Виджет внутри продукта с авто-диагностикой (FR-513). | P1 |
| FR-553 | **Email-to-post**: письмо на `feedback@`/`bugs@` создаёт обращение; автор определяется по адресу, вложения переносятся, ответы в треде становятся комментариями. Самый дешёвый способ включить в поток тех, кто никогда не зайдёт на портал. | P2 |
| FR-554 | API/вебхук из саппорт-инструментов (Intercom, Crisp, Telegram-бот, тикет-система). | P2 |
| FR-555 | Ручное создание админом от имени пользователя (пришло на звонке) — с указанием, от кого. | P2 |
| FR-556 | Импорт CSV при миграции. | P2 |
| FR-557 | Каждое обращение хранит `source`; в аналитике — разрез по каналам. Если 90% идёт из одного канала, остальные не работают, и это надо видеть. | P1 |
| FR-558 | Обращения из непубличных каналов (email, саппорт) по умолчанию **не публикуются**: попадают в триаж, и уже команда решает, выносить ли в публичную ленту. Автоматическая публикация чужой переписки недопустима. | P1 |

## 5. Приватность и хранение

Багрепорты — самая чувствительная часть портала: в скриншотах чужие данные,
в логах токены, в HAR — тела запросов.

| ID | Требование | P |
|---|---|---|
| FR-561 | Уровень приватности на обращении: `public` / `reporter+team` / `team_only`. Для `bug` по умолчанию публичны заголовок, статус и счётчик затронутых; описание, вложения и диагностика — `reporter+team`. Настраивается в конфиге продукта. | P1 |
| FR-562 | Retention: вложения и диагностика бага удаляются через N дней после закрытия (по умолчанию 90), сам пост остаётся. Иначе портал превращается в бессрочное хранилище PII. | P1 |
| FR-563 | Маскирование PII в тексте при вынесении обращения в публичное: email, телефоны, токены — предложить замену перед публикацией. | P2 |
| FR-564 | Приватные обращения — `noindex`, исключены из sitemap, недоступны публичному API. | P1 |
| FR-565 | Аудит-лог доступа к `security`-обращениям и к диагностике: кто и когда смотрел. | P2 |
| FR-566 | Экспорт и удаление данных пользователя включает его обращения, вложения и диагностику (NFR-08). | P2 |

## 6. Что осознанно не делаем

- **Автоматический приём краш-репортов из продакшена.** Это задача Sentry/Crashlytics,
  а не портала фидбэка: другой объём (миллионы событий), другая модель хранения.
  Интеграция — да (создать обращение из группы ошибок Sentry по кнопке), приём потока — нет.
- **Публичный список всех багов по умолчанию.** Включаемо флагом, но не дефолт: без
  фильтрации это витрина проблем продукта, и она демотивирует и пользователей, и команду.
- **Автоматическое воспроизведение багов / генерация тестов по репорту.** Заманчиво, но
  это отдельный продукт.
