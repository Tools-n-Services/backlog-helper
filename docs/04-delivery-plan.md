# План поставки

Принцип нарезки: каждый этап заканчивается состоянием, которое **можно отдать реальным
пользователям**. Никаких «этап 2 — бэкенд, этап 3 — фронтенд».

Порядок этапов следует трём контурам продукта (сбор → триаж → бэклог), а не порядку
экранов. Публичные украшения (роадмап, changelog) идут после бэклога сознательно:
без бэклога портал не даёт ответа на «что вы с этим сделаете», и роадмап нечем наполнять.

---

## Этап 0 — Каркас (0.5–1 день)

Инициализация Next.js + TypeScript + Tailwind + Prisma + Postgres в Docker, `config/product.ts`,
`theme/tokens.css`, layout с навигацией, CI (lint + typecheck + тесты), `.env.example`.

**Готово, когда:** `pnpm dev` поднимает пустой портал с логотипом из конфига,
`pnpm db:migrate` проходит на чистой базе, CI зелёный.

## Этап 1 — Контур сбора

Минимальный работающий цикл: пользователь пришёл, нашёл существующее обращение или создал
новое — идею или баг, — проголосовал, обсудил.

**Скоуп:** FR-101, 103, 111, 112, 115, 116, 118, 119, 120–124, 126, 131, 132, 136,
171, 172, 181, 182, 185, 501, 502, 503, 504, 506, 517, 551, 561 (базово), NFR-03, NFR-06.

Ключевые куски:
- схема БД из [02-data-model.md](02-data-model.md) **целиком**, включая `post_type`,
  `intake_source`, `attachment`, `backlog_item` и `insight`. Таблицы бэклога заводятся
  сразу, даже если UI появится на этапе 3: добавлять поля позже дешевле, чем переделывать связи;
- `post_type` с `form_schema` — динамическая форма по типу обращения. Это фундамент:
  прикрутить типы после того, как всё написано под один тип, — дороже вдвое;
- поля багов (`severity`, `frequency`, `environment`) и веб-форма с селектами окружения;
- `queries/feed.ts` с курсорной пагинацией, тремя сортировками и сортировкой по охвату для багов;
- `trend_score` — сначала расчёт в запросе, колонка и cron появятся на этапе 2;
- голосование через server action, гарантия — уникальный индекс, а не проверка в коде;
- **поиск похожих при создании** (`pg_trgm`) — не переносить на потом: без него с первого
  дня накопится база дубликатов, которую придётся разгребать руками;
- вход по magic link.

**Готово, когда:** на 5 000 сгенерированных обращениях лента открывается за < 500 мс;
повторный клик Vote не создаёт второй голос (есть тест); при создании показываются похожие;
баг и идея имеют разные формы, разные наборы статусов и разные сортировки по умолчанию.

## Этап 2 — Контур триажа

Здесь портал превращается из стены пожеланий в рабочий инструмент. Самый важный этап.

**Скоуп:** FR-102, 113, 114, 117, 133–135, 137–139, 141, 142, 145, 201–204, 211–215, 221,
231, 234, 301, 302, 305, 306, 309, 183, 184, 187, 505, 512, 531–537, 539, 540, 561–564.

Ключевые куски:
- админка: очередь триажа с авто-оценкой приоритета, список обращений с фильтрами
  (тип, статус, severity, priority, назначенный, просрочка), страница обращения с действиями;
- **решение по каждому обращению обязательно имеет причину, и причина уходит письмом.**
  `wont_fix` в тишину — главный способ убить доверие к порталу;
- `needs_info` с напоминанием через 3 дня и авто-закрытием через 14 (иначе очередь
  зарастает мёртвыми обращениями), реанимация ответом репортера;
- **merge с дедупликацией голосов + 301-редирект** строго по инвариантам
  [02-data-model.md](02-data-model.md#merge); тесты на пересекающихся голосующих,
  перенос комментариев, пересчёт счётчиков;
- смена типа обращения при триаже (пришло как баг — оказалось запросом функции);
- смена статуса → `status_change` → задача в очередь → письмо подписчикам
  с работающей отпиской и дебаунсом;
- pg-boss, воркер, cron на `trend_score`, `affected_count` и сверку счётчиков;
- уровни приватности обращения, вложения через подписанные ссылки, retention-джоба;
- метрики очереди на дашборде админки (время до первого ответа, возраст нетриаженного,
  доля `not_reproducible` и `duplicate`).

**Готово, когда:** админ проводит обращение по всем ветвям жизненного цикла, и на каждой
терминальной репортер получает письмо с причиной; merge не удваивает голоса; обращение
в `needs_info` без ответа закрывается само; падение почтового провайдера не откатывает
смену статуса; на дашборде видно, где очередь встала.

## Этап 3 — Контур бэклога

**Скоуп:** FR-601–605, 611, 612, 614, 615, 616, 631–636, 641, 642, 651–655, 222, 226.

Ключевые куски:
- `backlog_item` и связь N:M с обращениями; создание элемента из обращения одним кликом
  и привязка к существующему через поиск;
- агрегаты на элементе (суммарные голоса, уникальные пользователи, компании) с
  **дедупликацией пользователя через все join-ы** — см.
  [Reach и affected_count](02-data-model.md#reach-и-affected_count). На этом этапе Reach
  считается по голосам; инсайты подключатся на этапе 5;
- внутренние статусы + `status_map` и **односторонний** маппинг на публичные
  ([Маппинг статусов](02-data-model.md#маппинг-статусов)); письма только при смене публичного;
- ранжирование перетаскиванием (дробная индексация) поверх расчётного скора;
- RICE с настраиваемой формулой; представления: список, доска, матрица impact/effort;
- журнал решений с поиском;
- синк с трекером: создание задачи из элемента, вебхук обратно на внутренний статус.

**Готово, когда:** три обращения с разных досок связаны с одним элементом бэклога;
закрытие задачи в трекере автоматически двигает внутренний статус → публичные статусы
всех трёх обращений → письма их голосовавшим, и при этом промежуточные переходы
внутри трекера писем не породили.

## Этап 4 — Публичное лицо

**Скоуп:** FR-104, 140, 143, 144, 151–155, 161–167, 186, 232, 233, 303, 304, 405, 507, 508.

Роадмап (колонки по `show_on_roadmap`, фильтры, лимиты), changelog с типами/labels/RSS/
отложенной публикацией и **связью с обращениями** (публикация закрывает их и рассылает
голосовавшим), i18n-словари, роли, брендирование целиком через конфиг, импорт CSV,
изолированный поток `security`, маршрутизация `question` в саппорт.

**Готово, когда:** релиз публикуется из админки, связанные обращения становятся
`completed`, их голосовавшие получают письмо со ссылкой; форк разворачивается правкой
только `config/` + `theme/` + `content/` — проверено на втором продукте.

## Этап 5 — Масштабирование входа и приоритизации

**Скоуп:** FR-125, 128, 216–219, 223–225, 307, 308, 401–404, 406, 511, 513–516, 521–525,
538, 552–557, 621–625, 661–666, NFR-08.

- **Виджет-SDK с авто-диагностикой** + `fingerprint` и авто-дедупликация багов. Эти две
  вещи связаны: fingerprint работает только там, где есть диагностика. Вместе они
  радикально снижают долю `not_reproducible` — если после этапа 2 метрика показала,
  что она высокая, этот блок надо поднять в приоритете выше остального этапа 5;
- email-to-post и интеграции с саппортом — включают в поток тех, кто на портал не придёт;
- инсайты и их вклад в Reach; сегменты, компании, MRR-сортировка; vote on behalf;
- публичный API, вебхуки, embed-виджеты;
- SLA-политики и отчёты, аналитика (воронка, топ проблемных областей, доля релизов из фидбэка).

Делать по фактическому запросу конкретного продукта: этот этап легко превращается
в бесконечный, и половина функций может не понадобиться ни одному форку.

## Что мерить после запуска

Функционал портала бессмысленно оценивать по числу обращений. Смотреть надо на:

| Метрика | Зачем |
|---|---|
| Доля обращений без ответа команды за 30 дней | главный убийца доверия к порталу |
| Медиана времени до первого ответа | процесс триажа либо есть, либо нет |
| Доля закрытых как `duplicate` | > 25% → поиск похожих (FR-122/523) работает плохо |
| Доля закрытых как `not_reproducible` | растёт → нужна авто-диагностика (FR-513) |
| Голоса на обращение (медиана) | 1–2 → люди не находят существующие, создают свои |
| Обращений в `needs_info` дольше недели | очередь брошена |
| **Доля релизов, пришедших из фидбэка** | ключевая: показывает, работает ли третий контур или портал — отдел жалоб |
| Возвраты по письмам о смене статуса (CTR) | замыкается ли цикл «услышали → сделали → сообщили» |
