# Функциональная спецификация

Требования пронумерованы (`FR-*`) для ссылок из задач и PR.
Приоритеты: **P0** — без этого портал не работает, **P1** — без этого портал мёртвый через месяц,
**P2** — рост и приоритизация, **P3** — опционально/по запросу конкретного продукта.

Этот документ описывает **общий каркас** портала: доски, лента, обращения, комментарии,
роадмап, changelog, уведомления. Два ключевых для нашего фокуса блока вынесены отдельно:

- **типы обращений, приём и качество багрепортов, триаж** → [05-bug-intake.md](05-bug-intake.md) (`FR-5xx`);
- **формирование и приоритизация бэклога** → [06-backlog.md](06-backlog.md) (`FR-6xx`).

Термин «пост» ниже означает любое обращение — идею, баг или проблему; различия в форме,
статусах и видимости задаются его типом (FR-501).

### 2.5 Триаж и бэклог — в отдельных документах

Модерация (2.1) отвечает на вопрос «пускать ли это в публичную ленту». Дальше начинается
принципиально другая работа, описанная отдельно:

- **Триаж** — «что мы с этим делаем»: подтвердить, запросить информацию, признать
  дубликатом, отклонить с причиной, отправить в бэклог. Плюс SLA первого ответа
  и метрики очереди → [05-bug-intake.md, раздел 3](05-bug-intake.md#3-триаж).
- **Бэклог** — «в каком порядке делаем»: элементы работы, связанные с обращениями N:M,
  скоринг, ранжирование, синк с трекером → [06-backlog.md](06-backlog.md).
  Требования FR-221/222/226 из 2.3 — упрощённая версия «сортировки по важности»
  на уровне обращений, до появления полноценного `backlog_item` (этап 3).
  FR-223..225 (сегменты, компании, MRR) относятся к нему же и вынесены в этап 5.

## 5. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Публичные страницы: TTFB < 500 мс на p95 при 15k постов в доске. |
| NFR-02 | Один инстанс = один продукт (single-tenant, см. [03-architecture.md](03-architecture.md)). Никакого `tenant_id` в схеме. |
| NFR-03 | Все мутации идемпотентны там, где это осмысленно: повторный клик Vote не создаёт второй голос (уникальный индекс, не проверка в коде). |
| NFR-04 | Миграции БД — версионированные, вперёд-совместимые; форк обновляется из апстрима без ручной правки схемы. |
| NFR-05 | Логика не зависит от оформления: смена темы/вёрстки не требует правок в слое данных (см. правила форка). |
| NFR-06 | Rate limiting на все публичные мутации по IP + по пользователю. |
| NFR-07 | Загрузка картинок: лимит размера, whitelist MIME, вынос в объектное хранилище, не в БД. |
| NFR-08 | GDPR-минимум: экспорт своих данных, удаление аккаунта (FR-175), лог согласия на письма. |

## 6. Осознанно вне охвата (v1)

- Мультитенантность (один инстанс на много продуктов) — см. решение в архитектуре.
- Биллинг/подписки — портал не SaaS-продукт, а внутренний инструмент.
- Голосование без регистрации (анонимное) — ломает дедупликацию голосов и приглашает накрутку.
- Кредитное голосование/«N голосов на человека» — усложняет UX без доказанной пользы.
