# Установка: пошагово

Инструкция для того, кто ставит портал в первый раз. Быстрый старт — три
команды в [README](../README.md); здесь то же самое, но с проверками
на каждом шаге и с тем, что делать, если шаг не прошёл.

Времени занимает минут пятнадцать, из них десять — ожидание DNS.

---

## Шаг 0. Что нужно приготовить

**Сервер.** Любой Linux с Docker. Минимум — 2 ГБ памяти и 20 ГБ диска:
портал и воркер занимают немного, основное место уходит на базу и вложения.
Порты 80 и 443 должны быть свободны — их займёт прокси, и через 80 выписывается
сертификат.

**Домен.** A-запись на адрес сервера. Проверить, что она разошлась:

```bash
dig +short feedback.example.com
```

Пока команда не вернёт адрес сервера, дальше идти бессмысленно: сертификат
не выпишется.

**Канал почты.** Вход в портал работает только по письму, поэтому канал нужен
сразу. Варианты — SMTP вашей организации, Unisender Go или Resend. Для Resend
домен придётся подтвердить в их панели: до подтверждения письма уходят только
на адрес владельца аккаунта.

**Docker.** Проверить, что он есть и умеет compose:

```bash
docker version && docker compose version
```

## Шаг 1. Забрать файлы развёртывания

```bash
git clone https://github.com/Tools-n-Services/backlog-helper.git
cd backlog-helper
```

Исходники нужны не для сборки — образ берётся из реестра, — а ради
`compose.yml`, `Caddyfile` и `.env.example`. Если предпочитаете, скопируйте
только их.

---

## Шаг 2. Заполнить `.env`

```bash
cp .env.example .env
```

Три строки обязательны. Без любой из них compose откажется стартовать
и назовёт недостающую.

```
PORTAL_DOMAIN=feedback.example.com
POSTGRES_PASSWORD=<длинная случайная строка>
INSTALL_TOKEN=<длинная случайная строка>
```

Сгенерировать обе строки:

```bash
openssl rand -base64 24
```

Тут же — канал почты. Например, для Resend:

```
MAIL_PROVIDER=resend
MAIL_FROM="Название портала <feedback@example.com>"
RESEND_API_KEY=re_...
```

Остальное можно не трогать: хранилище по умолчанию файловое, перевод выключен.

**`INSTALL_TOKEN` — это ключ от свежего портала.** Пока установка не завершена,
кто угодно с этим токеном может назначить себя владельцем. Не отправляйте его
в мессенджере и не оставляйте в истории команд.

---

## Шаг 3. Запустить

```bash
docker compose up -d
```

Поднимутся четыре контейнера: база, портал, воркер и прокси. Первый запуск
занимает минуту-две — образ скачивается, база инициализируется, приложение
применяет миграции.

Проверить, что всё поднялось:

```bash
docker compose ps
```

У базы и портала в колонке статуса должно быть `healthy`. Если портал остался
`starting` дольше минуты — смотрите его журнал:

```bash
docker compose logs app --tail 50
```

Сертификат выписывается сам при первом обращении к домену. Если этого
не произошло, причина почти всегда в DNS или в занятом порте 80 — см. конец
инструкции.

## Шаг 4. Пройти мастер

Откройте в браузере:

```
https://feedback.example.com/install/enter?token=<INSTALL_TOKEN>
```

Пять шагов.

**Проверка среды.** Список с галочками: база, миграции, расширения поиска,
часовой пояс, запись в хранилище. Красная строка называет причину и что делать.
Пройти дальше можно и с ошибками, но перечисленное сломается позже —
и заметить это будет нечем.

**Продукт.** Название, знак в шапке, домен, язык по умолчанию. Всё это потом
меняется в админке.

**С чего начать.** Набор досок, типов обращений и статусов: полный, только
ошибки или минимальный. Выбор ни к чему не обязывает — состав правится позже.

**Почта.** Здесь мастер отправляет пробное письмо на адрес будущего владельца.
**Дождитесь письма и убедитесь, что оно пришло.** Это единственный момент,
когда почту можно проверить безболезненно: после установки вход в портал
работает только через неё.

**Владелец.** Почта и имя. После нажатия «Установить портал» вы окажетесь
внутри сразу — без письма. Так сделано намеренно: неверно настроенная почта
иначе запирает свежий портал, потому что войти некому, а починить настройки
можно только войдя.

Мастер после этого закрывается навсегда. Открыть его снова можно только сняв
отметку об установке в базе — через веб этого сделать нельзя.

## Шаг 5. Проверить, что всё работает

| Что | Как |
|---|---|
| Портал отвечает | Откройте `https://ваш-домен` — видна главная с досками |
| Вы владелец | В шапке есть вход в админку, в ней доступны «Настройки» |
| Воркер жив | `docker compose logs worker --tail 20` — видны названия проходов |
| Почта работает | Выйдите и войдите заново: ссылка должна прийти письмом |
| Копии | Настройте резервное копирование базы **сегодня**, а не потом |

Последнее — не формальность. Обращения клиентов сейчас существуют в одном
экземпляре, и копия, из которой ни разу не восстанавливались, копией
не считается.

```bash
docker compose exec -T db pg_dump -U backlog backlog | gzip > backup-$(date +%F).sql.gz
```

## Шаг 6. Первые настройки

Всё дальнейшее — в портале, без доступа к серверу:

- **Настройки** — название, разделы, лимиты, сроки ожидания ответа, цвет.
- **Доски** — состав и порядок; адрес доски после создания не меняется.
- **Статусы** — цвета из палитры, что показывать на дорожной карте.
- **Формы** — какие поля спрашивать в каждом типе обращений.
- **Люди** — роли: модератор, администратор, владелец.

Подробнее — в [пользовательской инструкции](11-manual.md).

## Обновление

```bash
docker compose exec -T db pg_dump -U backlog backlog | gzip > backup-$(date +%F).sql.gz
docker compose pull
docker compose up -d
```

Именно в таком порядке: миграции иногда меняют данные, и откат делается
восстановлением из копии, а не обратной миграцией.

Чтобы обновление было осознанным действием, а не следствием перезапуска,
укажите тег образа явно:

```
IMAGE_TAG=v1.2.0
```

## Второй продукт на том же сервере

Копия каталога со своим `.env` — другой домен, другой пароль базы, другой токен:

```bash
cp -r backlog-helper backlog-helper-second
cd backlog-helper-second && $EDITOR .env
docker compose -p второй-портал up -d
```

Тот же образ, своя база, свой домен. Общего у продуктов ничего: всё, что
их различает, живёт в их базах. Порты 80 и 443 занимает первый прокси —
второму продукту нужен либо свой сервер, либо общий прокси с двумя доменами
(тогда `proxy` из второго compose нужно убрать, а домен добавить в первый
`Caddyfile`).

## Если что-то не так

**Сертификат не выписался, браузер ругается.** Проверьте `dig +short домен` —
A-запись должна указывать на сервер. Затем `docker compose logs proxy` —
Caddy пишет причину прямым текстом. Частая причина: порт 80 занят другим
веб-сервером, а через него идёт проверка владения доменом.

**`/install` отдаёт 404.** Либо `INSTALL_TOKEN` не задан в `.env` — тогда
мастера не существует вовсе, и это защита, а не ошибка; либо установка уже
завершена. Проверьте, что заходите по адресу `/install/enter?token=…`,
а не `/install`.

**Портал не стартует, в журнале ошибки миграций.** Скорее всего база создана
без нужной локали. Она задаётся при инициализации кластера и потом
не меняется — базу придётся пересоздать: `docker compose down -v` удалит
и данные, поэтому делайте это только на пустой установке.

**Письма не приходят.** Первым делом — воркер: `docker compose ps` и
`docker compose logs worker`. Без него письма встают в очередь и молча никуда
не уходят; выглядит это как проблема почтового канала. Если воркер жив —
смотрите его журнал: канал пишет причину отказа.

**Вложения исчезают после перезапуска.** Проверьте, что том `uploads`
подключён (`docker compose config | grep uploads`). Для нескольких копий
приложения файловое хранилище не годится вовсе — нужен S3.

**Забыли, кто владелец, и войти некому.** Владельца можно назначить прямо
в базе:

```bash
docker compose exec -T db psql -U backlog backlog \
  -c "update app_user set access_role='owner', is_team=true where email='вы@example.com'"
```
