# Развернуть, настроить, обновить

Три раздела для трёх разных дел. Читают их в разное время и, как правило,
разные люди: разворачивают один раз, настраивают неделями, обновляют годами.

---

## Развернуть

Коротко. Пошагово, с проверками на каждом шаге и разбором отказов, —
[12-install.md](12-install.md).

Нужен сервер с Docker и домен, направленный на него A-записью. Дальше:

```
cp .env.example .env
docker compose up -d
```

В `.env` обязательны три строки — без них compose откажется стартовать
и скажет, какой именно не хватает:

| Переменная | Что это |
|---|---|
| `PORTAL_DOMAIN` | Домен портала. По нему Caddy сам выпишет сертификат |
| `POSTGRES_PASSWORD` | Пароль базы внутри compose. Наружу база не публикуется |
| `INSTALL_TOKEN` | Длинная случайная строка. Без неё мастер установки не существует |

Затем откройте `https://ваш-домен/install/enter?token=<INSTALL_TOKEN>`
и пройдите мастер: проверка среды, название и домен, набор досок и типов,
пробное письмо, владелец.

После установки мастер закрывается навсегда, а владелец оказывается внутри
сразу — без письма. Это намеренно: неверно настроенная почта иначе запирает
свежий портал, потому что войти некому, а починить настройки можно только войдя.

### Что поднимается

Postgres с томом, приложение, воркер и Caddy. Миграции применяет приложение
при старте — отдельной командой их запускать не нужно.

### Что нужно знать до боевого запуска

**Без воркера письма не уходят.** Он ставит их в очередь молча, и «портал
не отправляет письма» — самая дорогая ошибка первой установки, потому что
выглядит как проблема почтового канала. В compose воркер поднимается сам;
если разворачиваете иначе — поднимите его отдельно.

**`STORAGE_PROVIDER=file` годится для одного инстанса.** Вложения лежат в томе,
и вторая копия приложения их не увидит. Для нескольких — S3 (`S3_ENDPOINT`,
`S3_BUCKET`, ключи).

**Почта настраивается переменными среды, а не в портале.** Мастер её
проверяет — отправляет пробное письмо и ждёт подтверждения, — но задать канал
может только тот, кто задаёт среду. Ключи в базе означали бы, что дамп базы
это утечка всех ключей сразу.

### Второй продукт на том же сервере

Копия каталога со своим `.env` и своим именем проекта:

```
docker compose -p второй-портал up -d
```

Своя база, свой домен, тот же образ. Общего у продуктов нет ничего: всё, что
их различает, живёт в их базах.

## Настроить

Настройка разложена по трём слоям. Это главное, что стоит понять про портал:
от слоя зависит, чем и когда правится.

| Слой | Что там | Как меняется |
|---|---|---|
| **Админка** | название, знак, домен, язык, разделы, лимиты, сроки ожидания ответа, фирменный цвет, доски и категории, статусы, типы обращений и поля их форм | на живом портале, сразу |
| **Среда (`.env`)** | адрес базы, канал почты и его ключи, хранилище, переводчик, токен установки | перезапуском контейнера |
| **Код (`config/*.ts`)** | виды полей формы, смысл системных полей, формула приоритета, палитра, правила вложений | пересборкой образа |
| **Никогда** | `slug` доски, `key` статуса и типа после создания | — ломает ссылки и историю |

Где что лежит в админке:

- **Настройки** — продукт, разделы, лимиты, сроки, оформление.
- **Доски** — состав, названия на двух языках, видимость, порядок.
- **Статусы** — состав, цвет из палитры, форма маркера, роль на дорожной карте.
- **Формы** — поля каждого типа обращений: состав, подписи, обязательность,
  варианты выбора.

### Где граница между админкой и кодом

**Вид поля — код, состав полей — данные.** Мастер и админка комбинируют
готовые виды (строка, текст, выбор, галочка, ссылка, окружение, вложения),
называют поля и делают их обязательными. Новый *вид* — скажем, «геометка» —
добавляется кодом.

Отдельно стоят **системные поля**: у них есть логика за пределами формы.
`severity` задаёт срок первого ответа и порядок очереди триажа, `environment`
уходит в диагностику, которая не видна публично. Их можно переименовать,
переставить и убрать из формы, но не превратить в другое поле: иначе
приоритизация начнёт считать не то, и заметить это будет нечем.

Всё остальное, что заведут в редакторе, — свободные поля. Они показываются
на обращении и уходят в письма, но в логику не лезут. Это и есть цена свободы
их заводить.

## Обновить

Версия установки — это тег образа.

```
docker compose pull
docker compose up -d
```

Миграции применит приложение при старте. Порядок действий стоит соблюдать
буквально: **сначала копия базы, потом обновление**. Миграции в этом проекте
авторские и иногда меняют данные; откат делается восстановлением, а не обратной
миграцией.

Что переживает обновление без вмешательства:

- **Настройки.** Ключ, которого в вашей базе ещё нет, приезжает из пресета
  новой версии — без миграции данных и без пустых значений на экране.
- **Разделы настроек, записанные не целиком.** Флаг, добавленный в новой
  версии, включится по умолчанию, а не окажется выключенным молча.
- **Справочники.** Доски, статусы и типы правились в вашей админке и не
  трогаются обновлением: пресет — значения для новой установки, а не то,
  к чему приводится существующая.

### Если у вас форк

Форк больше не обязателен: всё, что различает продукты, переехало в базу.
Он нужен, только если меняется код — виды полей, формула приоритета, палитра.

Тогда апстрим подключается вторым remote, а правки держатся в `config/` и
`theme/`. Версия, от которой собран форк, фиксируется тегом: без этого пять
продуктов через год превращаются в пять разных продуктов.

### Что делает CI

На каждый pull request — типы, линтер, юнит-тесты и сценарии против собранного
портала, всё на настоящем Postgres. На тег `v*` — сборка образа и публикация
в реестр репозитория.

Без этого правка в шаблоне не доезжает ни до одной установки — и это самый
дорогой из возможных исходов.
