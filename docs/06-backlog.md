# Формирование бэклога

Требования нумеруются `FR-6xx`.

## 0. Центральное решение: пост ≠ элемент бэклога

Соблазн — сделать бэклог «отфильтрованной лентой постов со статусом planned».
Так делать нельзя, и вот почему:

1. **Одну работу питают несколько обращений.** «Роллап полей», «сумма подзадач» и
   «агрегаты в формулах» — три поста, одна задача. Обратное тоже верно: большой пост
   разбивается на три этапа работы.
2. **Внутренняя формулировка ≠ публичная.** В бэклоге стоит «Агрегаты в формулах, фаза 1:
   числа и валюта», у пользователя — «Rollup Custom Field values from subtasks».
3. **В бэклоге есть то, чего нет в фидбэке** — техдолг, комплаенс, миграции. Они должны
   конкурировать за приоритет наравне, а не жить в отдельной таблице.
4. **Приоритизировать нужно работу, а не голоса.** Пост с 6 400 голосами и пост с 40 могут
   быть одной задачей на два дня.

Поэтому: `post` — публичный сигнал (голос пользователя), `backlog_item` — единица работы.
Связь N:M. Закрытие `backlog_item` закрывает все связанные посты и рассылает всем
голосовавшим — вот в этой точке и замыкается цикл обратной связи.

## 1. Элемент бэклога

| ID | Требование | P |
|---|---|---|
| FR-601 | Сущность `backlog_item`: заголовок, формулировка проблемы, тип (`feature`/`bug`/`tech`/`compliance`), владелец, внутренний статус, оценка, целевой релиз/квартал. | P1 |
| FR-602 | Связь с постами N:M. На элементе — список связанных обращений с их голосами; на посте — ссылка на элемент бэклога (команде видна всегда, пользователю — опционально). | P1 |
| FR-603 | Создание элемента из поста в один клик (с автозаполнением из поста) и привязка поста к существующему элементу через поиск. | P1 |
| FR-604 | Агрегаты на элементе считаются по связанным постам: суммарные голоса, число уникальных пользователей, число компаний, суммарный MRR, число багов и их severity. | P1 |
| FR-605 | Элемент без связанных постов допустим (техдолг) и не выглядит ошибкой. | P1 |
| FR-606 | Темы (`theme`) — группировка элементов бэклога в продуктовые направления, с агрегатами по теме. | P2 |
| FR-607 | Внутренние обсуждения на элементе (комментарии команды), отдельно от публичного треда постов. | P2 |
| FR-608 | Разбиение элемента на дочерние (фазы) с наследованием связей на родителе. | P3 |

## 2. Приоритизация

| ID | Требование | P |
|---|---|---|
| FR-611 | Скоринг RICE: `Reach × Impact × Confidence / Effort`. Компоненты хранятся отдельными полями, итог — вычисляемое поле, чтобы можно было пересчитать при смене формулы. | P2 |
| FR-612 | **Reach считается, а не вбивается**: число уникальных затронутых пользователей по связанным постам и инсайтам, с весами сегментов из конфига (например `enterprise = 5`, `paid = 2`, `free = 1`). Ручной ввод Reach — источник самообмана. | P2 |
| FR-613 | Денежный разрез: сумма `monthly_spend` компаний, затронутых элементом. Сортировка бэклога по нему. | P2 |
| FR-614 | Формула настраивается в конфиге продукта (RICE / WSJF / своя). Не хардкод. | P2 |
| FR-615 | **Ручной ранг поверх расчёта.** Порядок в бэклоге задаётся перетаскиванием (дробная индексация: новый ранг = среднее соседних, без пересчёта всей таблицы). Расчётный скор — подсказка и колонка для сортировки, а не приговор: продуктовые решения принимаются людьми. | P2 |
| FR-616 | Представления бэклога: ранжированный список, доска по внутренним статусам, матрица impact/effort. | P2 |
| FR-617 | Сохраняемые фильтры/представления («баги P0», «просят enterprise», «квартальный кандидат»). | P3 |
| FR-618 | Снапшот приоритетов на дату — чтобы можно было ответить «почему в марте мы выбрали это». | P3 |

## 3. Инсайты (фидбэк вне портала)

Большая часть ценного фидбэка приходит не в портал, а в саппорт, на звонки и в чаты.
Если приоритизация видит только портал, она видит самых громких, а не самых важных.

| ID | Требование | P |
|---|---|---|
| FR-621 | Сущность `insight`: цитата (фрагмент реального высказывания), автор, компания, источник (звонок/тикет/чат/интервью), дата, ссылка на исходник. Привязывается к посту и/или элементу бэклога. | P2 |
| FR-622 | Быстрое добавление инсайта: вставить цитату → выбрать/создать элемент бэклога. Должно занимать секунды, иначе им не будут пользоваться. | P2 |
| FR-623 | На элементе бэклога — блок «12 цитат от 9 компаний, суммарно $18k MRR» с раскрытием. Это то, что защищает приоритет на встрече лучше любого скора. | P2 |
| FR-624 | Инсайты учитываются в Reach (FR-612) наравне с голосами, без двойного счёта одного пользователя. | P2 |
| FR-625 | Импорт инсайтов из интеграций (Intercom/Slack/транскрипты звонков) — по кнопке из выделенного текста. | P3 |

## 4. Маппинг статусов

Внутренний рабочий процесс и публичное состояние — **разные оси**. «In code review»
пользователю не нужен и не понятен; ему нужно «делаем».

| ID | Требование | P |
|---|---|---|
| FR-631 | Отдельный набор внутренних статусов (`backlog → discovery → in_progress → review → done`), настраиваемый. | P1 |
| FR-632 | Таблица маппинга внутренний → публичный статус в конфиге. Смена внутреннего автоматически двигает публичный статус связанных постов. | P1 |
| FR-633 | Обратной автоматики нет: публичный статус меняется только через внутренний или вручную админом. Двусторонняя автосинхронизация статусов даёт петли. | P1 |
| FR-634 | **Письма пользователям уходят только при смене публичного статуса.** Внутренние переходы (`in_progress → review`) публичный статус не меняют и никого не спамят. Без этого правила портал начнёт рассылать по три письма в неделю и получит массовые отписки. | P1 |
| FR-635 | Закрытие элемента (`done`) переводит все связанные посты в терминальный публичный статус, опционально привязывает их к changelog-записи (FR-165) и рассылает голосовавшим. | P1 |
| FR-636 | Отклонение элемента (`rejected`) с причиной — причина уходит авторам и голосовавшим связанных постов. | P1 |

## 5. Журнал решений

| ID | Требование | P |
|---|---|---|
| FR-641 | Каждое терминальное решение по элементу и по обращению фиксируется: что решили, почему, кто, когда. Публичная и внутренняя формулировки — отдельные поля. | P2 |
| FR-642 | Поиск по журналу решений. Нужен ровно для одного, но постоянного сценария: запрос приходит повторно через полгода, и надо за 10 секунд найти, почему в прошлый раз отказали. | P2 |
| FR-643 | При создании поста, похожего на ранее отклонённый, показывать пользователю прошлое решение (в поиске похожих, FR-122). Экономит и его время, и время команды. | P3 |

## 6. Синхронизация с трекером

Портал отвечает на «зачем и для кого», трекер — на «как и когда». Дублировать
разработку в портале не нужно.

| ID | Требование | P |
|---|---|---|
| FR-651 | Создание задачи в трекере (Linear / Jira / ClickUp / GitHub Issues) из элемента бэклога одной кнопкой: заголовок, описание, ссылка на элемент, список связанных обращений с голосами. | P2 |
| FR-652 | Хранение внешней ссылки и внешнего статуса на элементе. | P2 |
| FR-653 | Вебхук трекера меняет внутренний статус элемента → маппинг (FR-632) двигает публичные статусы → уходят письма. Это вся автоматизация «сделали → сообщили», и она должна работать без участия человека. | P2 |
| FR-654 | Маппинг статусов трекера → внутренних статусов в конфиге. | P2 |
| FR-655 | Устойчивость к отвалу интеграции: очередь с ретраями, видимый признак «синк сломан», ручная пересинхронизация. | P2 |

| ID | Требование | P |
|---|---|---|
| FR-661 | Объём обращений по типам и каналам во времени. | P2 |
| FR-662 | Топ проблемных областей: категория × число обращений × severity. Отвечает на «где болит сильнее всего». | P2 |

## 8. Что осознанно не делаем

- **Полноценный трекер задач.** Ни спринтов, ни списаний времени, ни зависимостей задач.
  Граница: портал ведёт приоритизированный бэклог и связь с голосом пользователя,
  исполнение живёт в трекере. Размывание этой границы превращает продукт в плохой Jira.
- **ИИ-кластеризация обращений в темы.** Вернуться, когда обращений станет > 2 000:
  до этого ручная группировка точнее и дешевле, после — становится главной болью.
- **Автоматическое проставление приоритета без человека.** Скор — вход в разговор, а не
  его замена; автоматизация приоритета выглядит объективной и потому опасна.
